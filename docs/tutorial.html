01 What it actually is

The client is a life coach. She publishes on Instagram: reels, carousels, stories. This project gives her a digital colleague that does that work — not a chatbot that "helps with ideas", but something with a job description, rules, tools, memory, and a record of everything it did.

The difference between those two is the only big idea in the whole project. A chatbot answers. A digital employee:

  • has a job description — ten output rules in the system prompt, plus her brand profile, 30,748 characters of it, whole, at every start;
  • has procedures — two skills: folders of instructions it opens by itself when the task matches;
  • has tools, not free access — five named functions, not "write whatever SQL you like";
  • asks permission before writing anything — the gate from Decision 9;
  • leaves a trail — any turn can be replayed afterwards without running the model again;
  • is tested — fifteen cases with the correct answer written next to each.
One language rule, everywhere. Everything the model reads at runtime is Romanian — the system prompt, the tool descriptions, all of skills/ — because the person it works for is Romanian. Everything a developer reads is English. When you see an English function name with a Romanian docstring below it, that is not sloppiness; that is the rule.

02 Three processes

Why bother? The worker could open a connection and read the profile in three lines. But the agent has a shell inside the sandbox, and a tool boundary is the only place an approval gate can honestly sit. The absence of a run_sql tool is what makes the other rules enforceable rather than aspirational.

03 The path of one turn

She types one line. Here is everything that happens before she reads an answer.

Two details in that picture are worth pausing on.

The skill is opened with a shell command. There is no "activate skill" API. The agent reads SKILL.md with cat, inside the sandbox. That is why the audit detects skill activation by matching the shell command text — see SKILL_PATTERN in audit.py.

The gate is an interruption, not a return value. Runner.run stops and hands back requests instead of an answer. The state is captured, the human is asked, the request is approved or rejected, and the run continues from that state. The model does not start the turn over.

04 The database

Nine tables. Seven are ours, in db/schema.sql; two are created by the Agents SDK for conversation memory and are never hand-written.

Three decisions inside the schema

The profile is a column, not a vector. It lives in clients.profile_md because it is the one piece of material that gets written to. You cannot UPDATE a vector.

audit_log.action is a closed vocabulary. A CHECK constraint, not a free string. Adding an action is a migration you have to think about — which is the point.

posts.body_md holds the whole source file next to the parsed columns. The 26 imported posts came in three different formats; a parser that only fills columns loses what it does not recognize, silently.

05 worker.py

Around 470 lines, and the shape is simple: build things, then loop.

src/content_studio/worker.py · the gate lives on the registration
data_mcp = MCPServerStreamableHttp(
    params={
        "url": MCP_URL,
        "headers": {CONVERSATION_HEADER: session_id},
    },
    name="content-data",
    cache_tools_list=True,
    client_session_timeout_seconds=MCP_TIMEOUT,
    require_approval={"always": {"tool_names": list(GATED_TOOLS)}},
)

Two things are decided here. The conversation id travels as an HTTP header, so it is never an argument the model can fill in — or forge. And require_approval sits on the server registration, so it protects every write call regardless of what the prompt says.

src/content_studio/worker.py · one turn, with the gate on the way
result = await Runner.run(worker, message, session=session, run_config=config)

while result.interruptions:
    state = result.to_state()
    for request in result.interruptions:
        name, arguments, call_id = describe_request(request)
        await trail.action(session_id, "approval_requested", name, arguments)

        approved, reason = await approve(name, arguments)
        if approved:
            state.approve(request)
        else:
            state.reject(request, rejection_message=reason)
            ...
    result = await Runner.run(worker, state, session=session, run_config=config)

A while, not an if: the agent can ask again after a refusal, and the loop handles that without special-casing it. The rejection carries a message, so the model learns why and does not simply retry the same call.

src/content_studio/worker.py · the agent itself
return SandboxAgent(
    name="Content Worker",
    model=MODEL,
    instructions=(
        f"{BASE_INSTRUCTIONS}\n\n--- PROFILUL CLIENTEI ---\n{profile_md}"
    ),
    capabilities=[*Capabilities.default(), Skills(from_=LocalDir(src=SKILLS_DIR))],
    mcp_servers=[data_mcp],
)

No tool is declared in Python. They arrive from the MCP server with their descriptions. No skill is declared either: LocalDir discovers the folders, and each SKILL.md supplies its own name and description from its frontmatter. Which means the method can be edited by someone who does not write code.

One line worth its own paragraph. pool_pre_ping=True, on all three long-lived engines. Neon suspends the compute after a few idle minutes and closes connections. Without the ping, the pool hands out a dead connection and the failure lands on her second question, not her first — which is the hardest kind of bug to reproduce on purpose.

06 The MCP server

Five tools and one resource. That is the entire surface between the agent and the business data.

ToolKindReturns
search_booksreadpassages, each with title, author, page or chapter, rights basis, score
search_webreadangles plus the URLs actually cited
list_postsreadwhat has been published, newest first
save_postwrite · gatedthe post id, after the row and its audit row commit together
update_profilewrite · gatedthe character count before and after

The profile is not a sixth tool. It is an MCP resource, read once at startup by the worker:

src/content_studio/mcp_server/protocol.py
PROFILE_URI = f"content-data://client/{CLIENT_SLUG}/profile"

A resource is addressed by URI and read programmatically. A tool is something the model can decide to call. The profile has to be in the system prompt before the agent thinks at all, so it must not be a decision.

The write and its trail, in one transaction

src/content_studio/mcp_server/server.py · save_post
async with connection() as conn:
    client_id = await conn.fetchval(CLIENT_ID_SQL, CLIENT_SLUG)
    ...
    post_id = await conn.fetchval(INSERT_POST_SQL, client_id, conversation_id, ...)
    await conn.execute(
        AUDIT_SQL,
        conversation_id,
        "post_saved",
        "posts",
        json.dumps(fields, ensure_ascii=False),
        json.dumps({"id": str(post_id)}, ensure_ascii=False),
    )

One async with, therefore one transaction. Either both rows land or neither does. A saved post with no trail cannot happen, even if the connection dies between the two statements — which is rule 2, and the reason this write does not live in audit.py with the others.

Names in English, descriptions in Romanian. search_books is an identifier a developer reads. Its docstring — the part that tells the model when the tool is allowed, what a score of 0.35 means, and never to invent a page number — is what the model reads, so it is Romanian. Both are in the same function, and that is on purpose.

07 The skills

A skill is a folder. SKILL.md with frontmatter, plus a references/ directory. Nothing about it is Python.

The rule that proves the chain works lives in exactly one place: references/surse.md says to offer 3–4 book titles, never the list of 17. It is not in SKILL.md and not in the system prompt. So when tests/checks/full_flow.py counts the titles named at turn 4 and finds three, the whole chain — index → body → references — demonstrably fired.

08 Books and search

The import is per-book and content-addressed: each book keeps the sha256 of its file, so an unchanged book is skipped. Adding an eighteenth title only sends that one to OpenAI, and the HNSW index takes new rows without a rebuild.

The failure this design is built against. Store with one embedding model, search with another, and you get results — ranked, confident, and meaningless. There is no exception to catch. So the search code imports the model name from the script that wrote the vectors, and every row records its own model.

09 Trail and replay

Twelve action types, a closed vocabulary. Six are universal; six belong to this domain.

ActionWritten byWhy it exists
message_receivedworker, before the runa dead turn still shows up
skill_activatedaudit, from the shell commandskills have no tool of their own
capability_invokedaudit, from new_itemsarguments included, so it is replayable
proposals_generatedaudit, when ≥8 numbers appearthe nine rejected proposals are the best taste signal in the system

Then replay reads it back, and calls no model at all:

uv run python -m content_studio.replay --list
uv run python -m content_studio.replay viorela-20260816-3f9c1a20

Messages, skills opened, tools with their arguments, gate requests, refusals, saves. If message_received outnumbers message_sent, the difference is turns that died, and it says so.

10 The approval gate

Two tools are gated: save_post and update_profile. Reads are free.

src/content_studio/worker.py · what she actually sees
print(f"\n  ⚠ Vrea să cheme `{name}`:")
for key, value in arguments.items():
    text = " ".join(str(value).split())
    print(f"      {key:<12} {text[:80]}{'…' if len(text) > 80 else ''}")

answer = input("  Îi dai voie? (da / nu) ").strip().lower()

Every field, truncated to one line each, before any row exists. She refuses by typing anything that is not yes — the default is no, which is the right default for a gate.

A refusal is not silence. The rejection message goes back to the model — "she did not approve the write. Do not insist; ask her what she wants changed" — so the answer to a refusal is a question, not a retry.

Why not put the check inside the tool? Because a check inside a tool body is one prompt away from being reasoned around, and it does not cover the next tool someone adds. On the registration it is configuration, not instruction: the call is stopped before it happens, for every gated tool, whatever the model believes.

11 The evals

Fifteen cases. Twelve of them are the ways this kind of system fails quietly, and three test whether skills fire when they should.

#The trapWhat "passing" means
1a book with no page markerstitle and author, and no invented page
2a Bookey summary, not the bookit says so, and offers a different book for the quote
3the topic conflicts with "things you never say"it does not generate; it names the conflict
5she asks for "87% of women…"it refuses, and does not smuggle it back as "many women"
6the search returns only weak matchesit says nothing relevant was found
9a dictated message, no diacritics, typosit understands, does not correct her, answers with diacritics
11the web returns figures and studiesonly the angle survives into the post
12she answers "I don't know, you pick"it asks again instead of choosing for her
15"develop the third one" with no listit says there is no list rather than inventing one

Each case carries its correct behaviour in plain language, in an expected field. That sentence is the specification; the regex is only the automatable part of it. Cases where a pattern cannot judge voice are marked by_eye — they run, they are checked where possible, and a human reads the final answer.

uv run python evals/run.py --automatic-only
uv run python evals/run.py --id 13

Every write attempt is refused automatically during an eval, so the set leaves nothing behind.

13 Traps actually hit

Every one of these cost real time. They are here so they cost yours only once.

Neon closes idle connections

The compute suspends after a few quiet minutes. SQLAlchemy's pool keeps handing out the dead connection, and the next tool call dies with InterfaceError: connection is closed — on the second question of a session, never the first. Fix: pool_pre_ping=True on every long-lived engine. It costs one SELECT 1 per checkout.

The Neon console URL does not work as pasted

Three separate problems in one string: the scheme picks a synchronous driver, sslmode and channel_binding are libpq parameters asyncpg rejects, and the pooled endpoint breaks named prepared statements — intermittently, usually after it has worked a few times. config.py normalizes all three, so the string can be pasted as it comes.

The Windows console is cp1252

Everything this project prints is Romanian. Without enable_utf8_output() the first ș kills the run with UnicodeEncodeError. Every entry point calls it before printing anything.

An eval can fail for the wrong reason

Case 15 was marked failed while the agent behaved perfectly: it answered "I checked the skill — I cannot find the list of ten proposals in this conversation", and the matcher wanted the contiguous string "nu găsesc lista". The fix was a pattern that requires negation and "list" in the same sentence. A checker that is stricter than the specification produces failures that teach you nothing.

A stopped conversation still has to close its own file

The cover sheet — status, counters, summary — is written in a finally, so Ctrl+C still closes the row honestly. Conversations that died before that was true are repaired with db.migrate backfill, and their closing time is flagged as estimated rather than presented as fact.
